Automation Project Proposal

Training Buddy — a Claude Code Plugin for Running the 2-Week Training Plan

Ad-hoc Activity Plan, Item 4  ·  Prepared by Leander  ·  2026-08-24

Problem

The 2-week training plan is a concrete, recurring workflow: the EM generates the plan — baseline assessment, daily topics, a graded retest at the end — and the mentee runs it. Today only the generation side has tooling; the running of it is manual per mentee: self-study, no structured assessment between Day 1 and the retest, and progress reporting written by hand. Meanwhile the naive way for the mentee to use AI — "Claude, teach me X" — fails in a specific, predictable way: it hands over answers. That optimizes for finishing the task, not for being able to reproduce the reasoning later without the AI in the room — which is exactly what the plan's graded retest tests.

Proposed project

Training Buddy is an installable Claude Code plugin tailored to the 2-week training plan: its input is the plan the EM already generates, and it runs the mentee side of it. The loop is mapped to the plan's actual shape — Day 1 baseline captured, daily topic days driven by the plan, and retest prep driven by the weak-spot list rather than by re-reading everything. It is format-specific but topic-agnostic: the plan supplies the material and assessment format, the plugin supplies the discipline.

Loop stageWhat it automates
/day-startOrientation from the generated plan — today's objective, prerequisites, time budget — plus a warm-up quiz on yesterday's material.
/quizSocratic quiz, one question at a time, answers withheld. Escalates recall → application → "what breaks if…". Every miss is logged.
/explain-backFeynman drill: the learner explains a concept in their own words; Claude grades it and names the gaps.
/drillA timed practice exercise matched to the growth area, critiqued against a rubric afterward — a whiteboard prompt for system design, a broken scenario for debugging, a review exercise for code quality, a mock stand-up for communication. Drill types are defined in the plan file, not hardcoded.
/day-endVerifies the day's evidence exists on disk, updates the status file, drafts the EOD report.

Two assets ship with the loop, and they are what make it actually work:

  • The buddy contract as plugin rules — no implementation code until the learner states an approach first, open design questions get turned back into questions, quiz comes before the build session. This is the discipline vanilla AI usage lacks.
  • A persistent weak-spot list — every quiz miss is logged (what was answered vs. what is true), and retest prep drills that list instead of re-reading everything.

Progress stays EM-visible without any new tooling: each day produces a committed evidence trail (journal, deliverables, EOD draft) — the same pattern my plan used for its daily reporting.

Why this project

The prototype predates the proposal. This loop already ran one full training plan end-to-end — my recent 2-week plan — as a set of custom Claude Code commands and a written working agreement, and the evidence is in that repo: a weak-spot list that tracked 21+ gaps, and a final retest answered with a question-by-question comparison against the Day 1 baseline. That version is hardwired to one learner and one plan; the project is extracting the loop, making it topic-agnostic, and packaging it — not invention. It also fits where the company is already heading: Claude masterclasses and hands-on workshops are running now, and this gives engineers a concrete, disciplined way to apply Claude to their own growth areas — an AI learning activity that speeds up learning, per the activity item. And it slots into the AI work already emerging around these workflows: with a PoC for interview sessions in progress and the training plan itself EM-generated, this covers the remaining manual stage — the two weeks where the learning actually happens.

Phased scope

PhaseScopeDepends on
MVP Build the plugin against the actual 2-week plan format the EM generates: the core loop reading the generated plan directly, configurable drill types per growth area, a generic weak-spot and status format, documentation. Pilot on one real generated plan — ideally a topic different from mine, to prove the loop is topic-independent. Nothing — the loop is proven, the material exists.
Phase 1.5 The EM side: baseline and retest grading assist against the plan's own targets, plus a per-mentee weak-spot/progress rollup — so plan generation and plan review are both cheap, not just generation. MVP pilot feedback.
Phase 2 Growth Portal integration: pull course and objective context so /day-start can point at relevant GP courses; optionally post completion or comprehension signals back to GP. A GP API being available.

Risks and mitigations

  • Learners can bypass the contract by asking vanilla Claude. The plugin cannot prevent that — instead it makes the disciplined path the convenient path, and the evidence trail (quiz logs, weak-spot list) shows whether the loop was actually run.
  • Overfit to my plan and topic. The MVP explicitly includes a pilot with a different engineer on a different topic; generalization is not done until that runs clean.
  • GP integration may not be possible. It is phased last, and the plugin is fully useful without it.

Proposed next step

If the direction looks right, I would start the MVP — roughly a one-week time-box at the same daily hours as the course work. Two things would help: a sample of a generated 2-week plan (any topic) to build the ingestion against, and a pilot — one mentee with an upcoming or active plan willing to run it through the plugin. I will propose a concrete schedule once the scope is agreed.
